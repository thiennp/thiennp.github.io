Architecture Case Study

Agent Witch

A control plane for running AI coding agents on real hardware — not only inside the IDE.

The Problem

Most AI coding agents run wherever the IDE happens to be open. That's fine for a solo developer, but it breaks down for a team: there's no shared run history, no way to dispatch a task to a teammate's machine, no audit trail, and no policy layer over who can run what. Agent Witch exists to give a team a single place to trigger trusted agent runs on real hardware — a Mac they own, not a shared cloud sandbox — with the same rigor you'd expect from any internal platform: authentication, approvals, and a record of what happened.

Deployable names (AWC/AWL/AWB/AWI) as used internally — a console, a Mac-local app, a Mac loopback bridge, and the install bundle.

Realtime Bridge & Security

The browser talks to a centralized Cloud Control Plane (AWC), which stays decoupled from the actual worker: each Mac runs its own client and a local bridge that dispatch and stream terminal output back over a WebSocket connection, not a plain REST poll. That connection is deliberately hardened at the transport layer rather than left to application-level checks: the server rejects any upgrade unless the request came in over HTTPS in production, and it checks the request's Origin header against an allow-list derived from the app's own configured host before ever handing the socket to the application. A duplicate or spoofed origin never reaches the dispatch logic at all — it's refused at the upgrade handshake.

Durable Workflow & Human-in-the-Loop

Longer workflows aren't modeled as one monolithic prompt. They're a persisted step graph that alternates operator checkpoints — a human approves or edits before the next step — with bounded agent dispatches, so a multi-hour operation can survive a browser refresh or a laptop closing. At the level of a single run, the same idea shows up as a mid-run input protocol: when the agent's output contains a specific marker asking a question, the run pauses, the pending state is written to disk, and the browser is asked to answer over the socket. Nothing about the run's accumulated output is lost while it waits — the process is stopped cleanly and resumed with full context once an answer arrives, rather than starting over.

Operational Hardening

A Mac is meant to run exactly one bridge process per install. To enforce that without a heavier coordination service, the client walks the local process table (ps -axo pid=,command=), matches other processes against the exact bundled script path for that install directory, excludes its own ancestor chain so it never signals its own parent, and sends a graceful termination to any sibling it finds. A watchdog LaunchAgent checks every 60 seconds that the client is still alive and restarts it if not, and a separate self-update LaunchAgent checks hourly for a new install bundle — so a stale or crashed client on someone's Mac doesn't sit broken until they notice.

Trade-offs I’d Call Out

Origin allow-listing over mTLS: checking the Origin header is cheap and easy to reason about, but it's an application-layer control, not a cryptographic one. A compromised browser extension that can forge headers is a threat model this doesn't fully cover — mutual TLS between AWC and each Mac client would close that gap at the cost of a much heavier install/rotation story.
Process-table matching over a lockfile: scanning ps output to find duplicate clients is portable and needs no extra state, but it's inherently best-effort — a renamed binary or a container boundary could evade the match. A PID file with an flock would be more precise, at the cost of one more thing that can go stale on a hard crash.

Neither is wrong for what this system needs today — a small number of trusted company Macs, not an adversarial multi-tenant fleet — but they're the first two things I'd revisit if Agent Witch's threat model grew.
